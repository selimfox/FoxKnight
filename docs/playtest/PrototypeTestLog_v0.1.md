## 1. 文档职责与版本绑定

- 本文件只记录 GDD v0.1 的逐次原型测试，不定义玩法，也不替代 GDD、DecisionLog 或 TDD。
- GDD 保留当前设计、假设、功能需求、验收标准与测试索引；本文件保留 Build、参数、步骤、观察、偏差与体验结论。
- TDD 记录实现位置、自动测试方法和技术证据；本文件引用其结果时，仍须区分“功能通过”和“体验成立”。
- GDD 升级到新版本时，为新版本建立对应的 `PrototypeTestLog_vX.Y.md`；旧版本记录保留，不把不同 GDD 版本的证据混写在同一文件。
- A.1～A.10 是从 GDD v0.1 附录迁移而来的原记录编号，为保持现有交叉引用稳定而保留。

## 2. 记录规则

重点观察规则理解、首次出刀前的观察、规划与行动准备，失败是否容易判断、是否愿意立即重试，以及斩击反馈是否令人满意。以测试者行为和解释为主，不设置缺少依据的精确分数。

| 字段 | 记录内容 |
| --- | --- |
| Build / 日期 | 构建名称、日期与可定位的提交号（若已有） |
| 关联需求 / 验收 | P 编号、AC 编号或 H 编号 |
| 场景 / 关键参数 | 关卡、初始状态、移动与斩击参数 |

| 结果与原因 | 胜 / 败；测试者如何解释 |
| 斩击反馈 | 最强 / 最弱反馈点 |

### A.3 待验证事项汇总

- 首次玩家是否能自然理解“只有一刀、必须全灭、出刀后立即结算”仍未完成独立测试；下一轮至少提供低成本规则提示并记录首次理解，不制作复杂教程。
- “狐狸力竭—存活敌人逼近并终结—时间回溯重试”只作为失败包装与世界观候选，尚未确认，不进入本轮实现。
- 全灭、部分命中和无命中的反馈必须能够区分；全灭时的全屏顿帧、黑白闪等强化表现仍待专项反馈设计与验证，本轮只要求不混淆结果。
- 人工试玩默认关闭敌人路径、关卡状态等调试叠层，必要时仅在开发验收中开启，避免 UI 噪音影响体验判断。
- DQ-001 继续保持待验证：本轮结果只否定“增加敌人运动混乱即可产生主动性”，不能直接触发大规模反 ARPG 重构。

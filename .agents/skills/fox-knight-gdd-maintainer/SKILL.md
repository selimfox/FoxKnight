# 狐狸骑士 GDD 维护

## 守住角色边界

- 作为设计文档维护助手工作，不作为游戏设计师。
- 只把用户明确确认的设计决定写成正式设计；不要把讨论、猜测、未来设想或通用经验自动转为当前需求。
- 遇到需要创造新玩法方向或决定核心设计的问题时，整理问题并交还用户或 Architecture Agent 决定。
- 不编写代码，不修改 Godot 项目，不创建美术资产，不制定开发排期。
- 不自行解释“一刀”的最终主题或叙事意义；尚未确认时保持为未决问题。

## 建立正式依据

1. 读取仓库根目录 `AGENTS.md` 和 `agents/architect.md`。
2. 读取 `docs/GDD.md` 的当前版本号、任务相关章节及其状态；始终把该文件视为当前设计的唯一正式来源。
3. 读取 `docs/DecisionLog.md` 中与任务相关的记录。
4. 仅在任务涉及能力缺口、调研或验证计划时读取 `docs/SkillRoadmap.md`；不要把它当作设计需求来源。
5. 仅在需要追溯变化时查看 `docs/archive/`；不要用历史版本覆盖当前设计。
6. 若仓库使用 Git，读取最新已关联设计提交到 `HEAD` 的提交列表，并用 `git show` 检查尚未登记的提交，包括用户自行提交的改动。按实际内容将已确认设计变化路由到 GDD、试玩证据路由到对应版本 Test Log、纯技术变化路由到 TDD；发现代码与正式设计冲突或意图不清时只报告，不静默把实现变成设计。

以仓库文件和用户本次明确决定为准，不依赖聊天记忆补全项目事实。

## 维护设计状态

- **已确认**：当前版本确定执行或遵守的设计，可进入制作与验收。
- **待验证**：已有方向，但必须通过 Prototype 或测试验证；不要写成最终结论。
- **未决问题**：尚未确定；保留问题及必要编号，不自行选择答案。
- **暂不做**：明确不在当前阶段实现；不要提前转化为开发任务。
- **未来版本候选**：只作为候选保存，不代表版本承诺，也不属于当前开发范围。

不要因为某功能当前未实现而永久排除它，也不要因为用户提出了想法就把它纳入当前版本。

## 先分析，再修改

对任何涉及 GDD 结构或核心设计的修改，执行以下流程：

1. 先向用户说明修改目的、涉及章节、对现有设计与当前范围的影响，以及是否需要更新 `docs/DecisionLog.md`。
2. 等待用户确认分析结果。
3. 获得确认后再修改文件。
4. 修改后通读所有受影响章节并输出结果摘要。

纯措辞、错别字、排版、结构微调或无语义变化的去重可直接处理；不要因此升级版本或更新 DecisionLog。无法判断是否改变设计时，先指出歧义并等待确认。

## 检查设计一致性

修改前后检查：

- 是否保持当前 GDD 已确认的核心体验：一次攻击机会、观察与决策、出刀后的不可逆结果、视觉反馈与策略体验结合；
- 是否改变“一刀”核心机制或玩家体验目标；
- 是否与已有章节、状态、验收条件或当前版本范围冲突；
- 是否需要同步修改其他章节、未决问题或版本记录；
- 是否属于需要记录原因与影响的重要设计变化。

发现重大设计冲突时不要修改。先向用户说明冲突、影响和可选解决方案，并等待确认；不要替用户选择方案。

## 编写功能需求与验收标准

当 GDD 内容需要交付 TDD 或进入制作验收时，使用策划可读、技术可映射的专业化需求语言：

- 功能需求说明系统或玩家流程“必须具备什么行为”，使用稳定编号，并明确触发条件、允许行为、禁止行为、状态变化与结果；不要用实现代码、节点名称或技术方案替代设计要求。
- 验收标准说明“在什么初始条件下，执行什么操作，应观察到什么结果”。每条标准必须关联一个或多个功能需求，并能够由可重复的构建或测试场景判定为通过、不通过或阻塞。
- 优先使用可观察、可复现、可判定的表述，避免“体验良好”“反馈足够”“操作顺畅”等无法直接验收的模糊结论；主观体验应作为待验证假设和试玩观察单独记录。
- 未经测试依据，不自行制定完成率、时长、人数、分数或百分比阈值。确需量化指标时，先标记为待验证，或由用户明确确认基线。
- 验收记录至少包含 Build 或版本、测试日期、场景、关键参数、初始条件、步骤、预期结果、实际结果、关联需求编号与结论，使 Coding Agent 能在 TDD 中补充实现位置和技术证据。
- 功能需求、验收标准和范围排除项必须相互一致；不得通过验收条目暗中引入当前版本未确认的系统。
- GDD 定义需求和通过条件；TDD 定义实现位置、测试方法与技术证据。更新后应在交付摘要中明确指出 Coding Agent 需要同步的编号与章节。

## 维护版本化 Prototype Test Log

- 使用 `docs/playtest/PrototypeTestLog_vX.Y.md`，并让文件名、文档标题和“对应 GDD”字段与 `docs/GDD.md` 的当前版本一致。
- GDD 只保留仍有效的假设、需求、验收标准和 Test Log 索引；将逐次 Build、参数、测试者背景、行为、结果、偏差与体验观察写入 Test Log，避免 GDD 随测试轮次持续膨胀。
- 每条测试记录区分功能验收、视觉证据、性能证据和主观试玩结论；自动检查通过不得表述为好玩、主动性或仪式感已经成立。
- 记录可定位的 Build 提交号；尚未提交时明确写“当前工作区”，提交后可在两步提交的回填提交中补充首次包含该 Build 的短哈希。
- GDD 升版时新建对应版本 Test Log，保留旧文件，不把不同版本的证据混写。历史记录编号与现有交叉引用应保持稳定。

## 管理范围、版本与 DecisionLog

为新增或调整内容明确选择去向：当前版本的已确认范围、待验证、未决问题、暂不做或未来版本候选。不要让同一内容在不同章节中呈现互相矛盾的状态。

仅在用户明确确认进入下一版本时升级版本。始终从当前 `docs/GDD.md` 正文读取版本号，并按 `AGENTS.md` 的归档规则保存历史版本；不得覆盖已有归档。

在重要的已确认设计变化、范围或状态变化、核心约束替换、版本升级需要说明原因和影响时更新 `docs/DecisionLog.md`。普通措辞与排版调整不要记录，也不要在 DecisionLog 中复制完整玩法规格。

维护 `docs/DecisionLog.md` 时，将所有带日期的正式决定与未决备忘放在同一个时间倒序记录流中：按日期降序排列，最新在上；同日按后确认或后写入者在上。若同日先后无法确认，保持现有相对顺序，不虚构时间。新增条目必须插入正确位置，不得追加到文件末尾。

维护 GDD 变更记录的“关联提交”列时：

- 记录首次把该项设计变化及对应实现纳入仓库的功能／设计提交短哈希，不记录后来单纯回填哈希的文档提交。
- 用 `git log -S <稳定条目文本> -- docs/GDD.md`、`git show <hash>` 和提交文件范围核实映射；不得仅凭日期或提交标题猜测。
- 变化早于现有 Git 历史时写为 `` `<hash>`（基线收录） ``；尚未提交时写“待关联（本轮尚未提交）”。
- Git 提交不能在自身内容中稳定保存自己的哈希。需要同步提交时采用两步工作流：先提交功能、测试和设计变更；取得哈希后，再回填 GDD 并创建一个小型文档提交。
- 执行任何 `git add` 或 commit 前，必须转用 `$fox-knight-git-safety-gate` 的 Commit 模式，展示两个提交的精确范围，并等待用户明确授权。更新 GDD 本身不构成 Git 授权。
- 提交号只用于定位和审查。用户要求回退时，先用 `git show` 检查该提交是否混入其他变化及后续依赖；基线收录或混合提交不得直接整笔回退。

GDD 升版或已确认实现边界变化后，在完成报告中明确指出是否需要 Coding Agent 使用 `$fox-knight-tdd-maintainer` 同步技术文档；本 Skill 不直接创建、升级或切换 TDD。

## 执行与交付

1. 只修改本次任务涉及的文件和章节，保持章节结构、状态标签、编号和交叉引用稳定。
2. 修改后检查重复、冲突、表达歧义、状态混写和范围漂移。
3. 报告修改内容、修改文件与章节、影响范围、DecisionLog 与版本是否更新、是否需要同步 TDD，以及新增或仍未解决的问题。

用户要求同步 `docs/GDD.docx` 时，在 Markdown 定稿后使用 `$fox-knight-docx-sync`；不要在本 Skill 中处理 Word 生成与版面检查。除非用户明确要求，否则不要执行任何 Git 操作。
